## F-069 查看器自适应缩放

> 2026-11-02 用户截图与口述登记；状态「实现中」：F-074 默认原图已落地，大图默认按适应显示；显式适应/100% 标签与窗口重算验收待补。现有 F-002 覆盖缩放/平移/旋转/全屏/原图切换，本项补的是自动适应策略、模式入口与显示级预览。
> 2026-11-02 追加：双击/打开查看器默认直接加载原图（F-074）；显示级预览改为可选的快速模式/超大图兜底，不再作为默认源。

### 现象与复现

- 用户打开一张 1536×2360 的 PNG，内联查看器舞台约 1380×950；图片只显示约 333×512，工具栏显示 100%，四周大片留白（用户附件截图，2026-11-02）。
- 同一张图点「原图」后才切到原图/原图的 sRGB 预览；普通模式始终显示缩略图。

### 现状定位（按模块/函数）

- `viewer.rs::render_viewer`：`viewer_original=false` 时 `source` 取 `asset.thumb`（`tile_thumb` 兜底）；只有「原图」才走 `preview_state` 或原路径。
- `state.rs` 的图像缩略图路径为 `image.thumbnail(512, 512)`；ffmpeg 路径为 `scale=512:512:force_original_aspect_ratio=decrease`。所以查看器普通模式的源图长边最多 512，常见竖图就是约 333×512。
- `vendor/ely-gpui-components/src/media/viewer.rs`：`fit(picture, stage)` 取 `min(stage/picture)` 后再 `min(1.0)`；`View.zoom=None` 表示适应；图片源变化时重置为适应；舞台尺寸变化且 `zoom` 仍为 `None` 时会重算。
- 结果：缩略图小于舞台 ⇒ fit = 1.0 ⇒ 显示 100% 小图。缩放/平移/旋转本身正常，但用户感知不到“自适应”，因为自适应源本身只有 512px。
- 组件已有 `0`（适应）、`1`（100%）、`+/-`、`Ctrl+滚轮`、双击切换与 fit 按钮；查看器提示只写 `+/- 缩放`，没有暴露 `0/1`，顶部只显示百分比，无法区分“适应”和“手动 100%”。

### 目标行为（待确认）

1. 打开/切图默认「适应窗口」：整图完整可见、居中、不裁切；图片来源变化后重新适应。
2. 窗口、侧栏、检查器、底栏或全屏尺寸变化后，若仍在适应模式则重新计算；手动缩放过则保留手动缩放，直到用户点「适应」或按 `0`。
3. 模式与入口：`适应窗口` / `100%`（可选 `填充窗口`），支持 `0`/`1`、双击切换、工具栏按钮与状态标签（“适应”/“100%”/`×n%`）。
4. 显示质量：默认源由 F-074 决定——双击/打开查看器直接使用原图文件；显示级预览仅作为用户显式选择的「快速预览」或超大图兜底，不在默认路径把 512 缩略图放大。
5. 小图策略（需确认）：真实小图（例如 200×200）默认保持 100% 不放大；只对“快速预览源”使用按视口生成的高分辨率预览，避免混淆 100% 语义。
6. 视频/远端：视频只显示首帧，远端虚拟路径没有原图；仍可对现有位图做适应/100%，但不生成显示级预览。
7. 不破坏 F-064：预览仍在 `thumbs/previews`、临时、切图/关闭清理、不占 10GB 缩略图预算；不回到 gpui 全局资产缓存。

### 方案对比

#### A. 可选：适应模式 + 显示级预览

- core：新增/扩展显示级预览生成，复用 `color.rs::prepare_preview` 的 epoch 与清理骨架；按目标长边（建议 2048/2560，按 DPR 与舞台尺寸取桶）从原图后台解码、方向校正、缩放、转 sRGB；预览键包含尺寸桶与源 `mtime`/`bytes`；大图设像素上限，超限回退缩略图并提示。
- ui：默认源为原图（F-074）；「快速预览」模式下按 `ViewerZoomMode` 选择显示级预览，Actual 用原图；增加模式状态、按钮、快捷键与标签。
- vendor：给 `ImageViewer` 增加初始缩放/适应策略参数，或在外层包一个受控组件；保留“舞台变化重算”和“切图重置”，新增“手动缩放退出适应模式”的状态回报。
- 优点：大图/低内存机器上有可选的低成本路径；清晰度优于 512 缩略图。
- 风险：预览生成延迟、临时文件 I/O、超大图解码内存；需要竞态取消与清理；模式跨图持久化范围要先定。

#### B. 最小改动：放开 fit 的 1.0 上限

- 直接把缩略图放大到舞台尺寸；改动最小，但 512 缩略图放大会明显模糊，且真实小图会被错误放大。不建议作为最终方案，最多作为临时兜底。

#### C. 默认原图 + 异步 fit（F-074 采用）

- 双击/打开查看器直接使用原路径，gpui `ImageAssetLoader` 异步解码；加载期间显示中性的加载状态，不先显示处理后的缩略图；按原图像素做适应/100%。
- 优点：完全符合用户「不要处理后的」要求；保留最大细节；实现路径比预览管线短。
- 代价：全尺寸解码的内存峰值、广色域 ICC 在 gpui 中是否被尊重需实测、超大图加载时间；必须做像素上限/提示与切图/关闭释放。

### 复用结论

- 设计借鉴 ImageGlass 的 `AutoZoom` 默认与 Loupe 的 `FitMode` 状态机；实现保持在 MIT 的 vendored `ely-gpui-components` + `kanalib-core`，不复制 GPL 代码。
- 显示级预览优先复用 F-064 已有的 `thumbs/previews` 临时预览与 epoch 清理，不新建第二套缓存目录，不改变 10GB 缩略图预算口径。
- 先做“适应窗口/100%”两态 + 窗口重算 + 默认原图（F-074）；显示级预览作为可选“快速预览”与超大图兜底；`填充窗口` 作为可选第三态，待确认是否需要。

- **待确认 1（小图策略）**：真实小图是否允许放大？推荐“实际小图保持 100%，仅显示级预览按视口填充”。

## F-070 侧栏与标签工作区重构

> 2026-11-02 用户截图与口述登记；状态「实现中」：方案 C 最小收敛与侧栏浏览筛选分组重排已落地（去重复入口、标签页隐藏侧栏标签搜索、统一计数、查看图片/返回路径）；方案 A 工作区待定。目标不是新增标签能力，而是把现有的「浏览筛选 / 标签分配 / 标签管理」三层职责拆清：同一能力只保留一个入口，同一列表只保留一套搜索与计数口径。本次不改标签数据模型、别名/合并语义与 schema；也不重排主图库网格与查看器布局。

### 现象与重复点

- 活动栏的「标签」图标（`ActivityTarget::Tags`）、侧栏「整理 > 标签管理」、命令面板 `goto:tags` 三处都能打开同一个 `Screen::Tags`；其中活动栏图标叫「标签」，实际打开的是「标签管理」，与侧栏底部的「标签」筛选区同名不同义。
- `render_sidebar` 在 `Screen::Tags` 下仍渲染完整的资源管理器侧栏（来源/筛选/智能集合/相册/整理/评级/自动归类/标签）。标签页打开时，侧栏仍显示第二套标签搜索与分类 chips，页内又有一套搜索与使用频率筛选。
- 侧栏标签点击调用 `set_filter`，会把 `screen` 切回 Library。用户在标签页点侧栏标签会静默离开标签页，且返回时没有「回到标签工作台」的路径。
- 两套标签列表的筛选口径不同：
  - 侧栏：分类 chips + 搜索；只列 `count > 0` 且未屏蔽；默认 10 条、可展开到 200；标题计数取 `tag_vocab.len()`（含 0 使用/已屏蔽），与列表实际口径不一致；点击筛选图库，Ctrl/Shift 追加 `tag:` 搜索。
  - 标签页：全词表（含 0 使用/已屏蔽）；搜索名称+类别；按 `全部/0 使用/低频/仅自动` 筛选；支持排序、重命名、合并、屏蔽；没有「查看这些图片」的返回动作。
- 「整理」目前只有「重复项」和「标签管理」；「评级」「自动归类」「标签」这些浏览筛选被排在集合/整理之后，侧栏纵向顺序把“浏览”和“维护”混在一起。
- 右侧检查器的「手工标签/自动标签」是分配面，职责本身不与上述列表重复；但「搜索标签」「添加标签」「筛选标签」三个文案相邻，容易让用户误以为是同一件事。
- 「智能集合」是保存的查询，「相册」是手工归属，「自动归类」是按标签组派生的浏览筛选，三者不是重复功能；本次保留其数据语义，只调整它们在侧栏中的分组和说明。

### 目标设计（待确认）

1. **一个标签目的地**：活动栏的「标签」成为一等标签工作区（或明确改名为「标签管理」）；移除「整理 > 标签管理」重复入口；命令面板保留一个入口。

## F-072 搜索入口与搜索态收敛

> 2026-11-02 用户口述登记；状态「实现中」：已确认方案 A 并落地（移除活动栏搜索、补 Esc/清除/点击外部失焦），待补 UI 验收。目标：一个全局搜索入口、一个明确的搜索退出路径，避免左侧按钮与标题栏搜索框重复。

### 现象

- 活动栏的「搜索」图标（`ActivityTarget::Search`）并不打开搜索视图，只调用 `focus_search` 把焦点送到标题栏搜索框；它没有独立面板、结果页、状态或清除入口。
- 标题栏已经有实际搜索框，因此左侧图标与标题栏搜索框功能重复；用户感知为“搜索按钮功能很不完整”。
- 搜索框获得焦点后，只有点击图片网格才会把焦点移走；点击侧栏行、空白区域、标签页等不会主动失焦，搜索框一直保持高亮/焦点态。
- 没有 Escape 退出搜索的绑定：根级 Escape 走的是清除选择/关闭相似结果；`TextInput` 自身没有 Escape 关闭行为。`Ctrl+F` 只负责聚焦。
- 搜索作用域也不止一处：标题栏全局搜索、相似结果视图本地筛选、标签管理页标签搜索；文案相近但语义不同。

### 调研结论（详细对照见 [ui-refactor.md](../ui-refactor.md) 的搜索与键盘一节）

- Apple HIG：搜索字段应有清除按钮、明确的当前作用域；应用尽量只有一个主要搜索位置，局部搜索要能看出作用域。
- VS Code：独立 Search 视图只作为局部参考，不作为本项目目标；本项目采用图片管理器的单一搜索框 + 网格结果（见 [ui-refactor.md](../ui-refactor.md) 的参考层级）。
- Lightroom / Eagle / Finder：搜索框是单一位置，Esc/清除/点击其它区域都会结束编辑态；不会留下长期高亮。
- Linear / Notion / Obsidian：搜索/命令面板是独立浮层，Esc 关闭，键盘优先；与视图内筛选分开命名。

### 方案对比

| 方案 | 做法 | 结论 |
|---|---|---|
| A. 移除活动栏搜索图标（推荐） | 只保留标题栏搜索 + `Ctrl+F`；搜索框补 Esc/失焦/清除；左侧不再有重复入口 | 当前结果就在网格中，没必要再做第二个搜索入口；最小且一致 |
| B. 活动栏搜索升级为真正 Search 视图 | 点击后侧栏切换为搜索条件/历史，内容区显示独立结果 | 需要新的结果视图与状态，与现有网格搜索结果重复；成本高，且与“不以 VS Code 为主参考”的方向不符 |
| C. 保留图标但改名/加状态 | tooltip 改为「搜索（Ctrl+F）」，按下时高亮，点击仅聚焦 | 仍是重复入口，用户已明确指出“功能不完整”，不推荐 |

### 目标行为

1. 全局搜索只有一个常驻入口：标题栏搜索框；`Ctrl+F` 聚焦并全选，活动栏图标移除。
2. 搜索框在编辑态才显示焦点环；点击侧栏/内容/空白/其它控件时失焦，焦点环消失。
3. `Esc` 的语义：有查询文本时先清空查询并保持结果；再按一次或查询为空时退出编辑态；不改变当前选择。
4. 清除按钮（`clearable`）清空文本并保持焦点，用于连续修改；Enter 提交历史（如需）但不强制失焦。
5. 相似结果/标签页的本地搜索保留，但 placeholder 与按钮文案明确写“筛选相似结果”“搜索全部标签”，不与全局搜索混用。
6. 搜索历史下拉在失焦/Esc 时关闭；打开命令面板、设置、查看器时搜索框必须失焦。

### 验收

- [ ] 活动栏不再有“只聚焦标题栏”的重复搜索按钮（若保留则必须是独立 Search 视图）。
- [ ] 点击侧栏任意行、空白、标签页、设置页后，搜索框焦点环消失；只有点击图片/再次 Ctrl+F 才重新聚焦。
- [ ] Esc 清空/退出行为符合上述语义；清除按钮可用；查询文本与查询结果保持一致。
- [ ] `Ctrl+F` 聚焦并全选；搜索历史可打开、可选择、可关闭；命令面板/对话框打开时不会把焦点抢回搜索。
- [ ] 相似视图与标签页的本地搜索文案、作用域清楚，不与全局搜索混淆。
- [ ] 现有 F-010/F-015（搜索语法、历史/帮助）与键盘导航不回归。

### 风险

- GPUI 的焦点转移需要显式处理：侧栏行/空白区域不一定可获得焦点，可能需要根容器在鼠标按下时主动 blur，或给搜索框加 `on_blur`/Escape 处理。
- 全局点击失焦不能抢走对话框、文本输入或命令面板的焦点；需要按事件路径判断。
- Esc 同时被网格/查看器/相似结果使用，必须按当前焦点上下文分层，避免一次 Esc 触发多个动作。

- 不改搜索语法、索引与结果排序，只改入口与交互状态。

### 现状审计（详见研究文档）

- `theme.rs` 目前主要提供颜色与 3 个壳层尺寸；间距/字号/圆角/动效没有项目级 token，组件局部数值较多。

### 推荐原则

1. 内容优先：主图库与查看器继续最大化内容，控件退后；不为了“看起来新”增加装饰。
2. 一个能力一个入口：搜索、标签管理、主题、设置各自只有一个主入口（F-070/071/072）。
3. 上下文侧栏：侧栏随活动栏目的地变化，而不是任何页面都显示资源管理器。
4. 单一搜索：全局搜索一个位置；局部筛选明确标注作用域。
5. 渐进披露：高频动作直接可见，低频动作进菜单/更多；每个界面只有一个主操作。
6. 键盘优先：所有高频路径可用键盘完成；焦点可见、Esc 有明确语义。
7. 状态完整：空/加载/失败/禁用/加载中/无权限/超时都有明确视觉与下一步。
8. 克制视觉：沿用暗色底、细边框、少量 accent；用层级/留白/字重而非大圆角和大阴影。
9. 可访问与性能是验收项，不是收尾项。

## F-074 查看器默认加载原图

> 2026-11-02 用户口述登记；状态「实现中」：默认原图、快速预览、色彩管理三态已落地；宽色域、超大图与内存压力未实测。双击图库缩略图（以及快速查看）进入查看器时，默认直接加载原图文件，不显示处理后的 512 缩略图或 sRGB 预览。与 F-069（自适应缩放）配套。

### 现象与现状

- `handle_tile_click` 在 `click_count >= 2` 时调用 `open_viewer_at`；`open_viewer_at` 把 `viewer_original` 重置为 `false`。
- `render_viewer` 在 `viewer_original=false` 时 `source` 取 `asset.thumb`/`tile_thumb`（长边最多 512）；只有点「原图」后才走 `preview_state` 或原路径。
- 即使在「原图」模式，广色域文件也要等后台 `prepare_preview` 生成 sRGB 预览（`ViewerPreview::Ready`）后才会替换缩略图；等待/失败期间仍显示缩略图。
- 因此当前双击看到的是处理后的 512px 缩略图，不是原图，与用户预期不符。

### 目标

1. 双击缩略图/快速查看打开查看器时，默认源为原始文件（`asset.path`），不经过 `thumb`、`tile_thumb` 或 sRGB 预览管线。
2. 加载期间显示中性的加载状态（spinner/占位），不先闪一张处理后的缩略图；加载完成后按原图像素做 F-069 的适应/100% 缩放。
3. 保留显式的「快速预览」模式（原「预览」按钮），供大图/低内存场景手动选择；默认不再进入该模式。
4. 切图/关闭时释放原图资源；不把全尺寸解码结果留在 gpui 全局资产缓存中。
5. 视频、远端只读、缺失/损坏原图保持现有边界：视频首帧、远端占位、损坏提示；没有本地原图时不伪造原图。

### 方案对比

| 方案 | 做法 | 评价 |
|---|---|---|
| A. 严格原图（推荐默认） | 查看器 `source = asset.path`；`ImageAssetLoader` 异步解码；跳过 `prepare_preview`；加载期显示中性状态 | 最符合“不要处理后的”；保留最大细节；需要处理 ICC/内存风险 |
| B. 原图优先 + 色彩管理回退 | sRGB/untagged 直接原图；广色域先显示原图，另提供显式「色彩管理预览」；不静默转换 | 兼容 F-064；颜色更可控，但“原图”与“预览”语义需要清楚标注 |
| C. 原图 + 超大图降采样 | 原图直接加载；超过像素上限时提示并提供快速预览/降采样 | 保护内存；仍有“处理”分支，需用户确认 |
| D. 渐进显示（缩略图→原图） | 先缩略图占位，原图解码后替换 | 与“不要处理后的”冲突，不采用 |

推荐：默认 A；结合 B 的显式色彩管理选项和 C 的超大图保护，三者按“默认原图、显式预览、超大图提示”组合，不静默替换源。

### 调研来源 / 候选对比（截至 2026-11-02）

| 产品 | 查看源 | 缩放/渲染 | 对本项目的启示 |
|---|---|---|---|
| [ImageGlass](https://github.com/d2phap/ImageGlass) | 以原始图片为查看源；官方特性含硬件感知缓存、色彩管理与基础 HDR | 缩放/插值/缓存由查看器渲染层处理 | 本地查看器默认原图是常态；大图靠缓存/渲染层，而不是先显示缩略图 |
| [qView](https://github.com/jurplel/qView) | `QVImageCore` 加载原文件为 pixmap，fit/原始尺寸切换 | Qt GraphicsView 负责缩放/平移 | fit 原图、原始尺寸双态；没有“默认预览代理” |
| [GNOME Loupe](https://gitlab.gnome.org/GNOME/loupe) | glycin 解码原文件 | 分块/缩放渲染；BestFit 默认 | 原图 + 分块渲染可以兼顾大图；Rust 实现可借鉴思路，不复制 GPL 代码 |
| [Lightroom Classic](https://helpx.adobe.com/lightroom-classic/help/keywords.html) | 标准/1:1 预览，RAW 工作流 | 预览优先 | 反例：RAW 编辑工作流需要预览；本地图片查看器不应照搬“预览优先” |
| Web 图库（PhotoPrism/Immich） | 服务端生成预览 | 浏览器显示预览 | 反例：网络/服务端架构需要预览；本地桌面查看器可直接读原图 |

补充：本地桌面查看器（ImageGlass/qView/Loupe）普遍以原图为源，预览代理主要出现在 RAW 工作流、网络图库或超大图缓存场景。Kanalib 是本地优先，双击默认原图更符合用户预期。

### 技术方案（建议）

- `open_viewer_at`：把 `viewer_original` 的布尔语义改为显式的 `ViewerSourceMode::{Original, QuickPreview}`，默认 `Original`；双击/快速查看都走 `Original`。
- `render_viewer`：`Original` 直接 `source = path`（本地非视频/非远端）；`QuickPreview` 才取 `thumb`/显示级预览。移除“原图模式下先显示 thumb”的默认回退。
- 加载状态：`ImageViewer` 在 `picture=None` 时已有 spinner；确保源切换时旧图立即释放、显示加载态，不保留上一张或缩略图。
- 资源释放：沿用 `remove_viewer_asset`（path + thumb），切图/关闭时释放原图与预览；确认 gpui 的 `ImageAssetLoader` 缓存键按 path 清理。
- 色彩：先实测 gpui `ImageAssetLoader` 是否读取 ICC。若不读取：
  - 默认严格原图（用户要求），广色域图在提示中说明“未做色彩转换，颜色可能与系统预览不同”；
  - 提供显式「色彩管理预览」使用 F-064 的 sRGB 预览，不静默替换。
- 超大图：设置像素/字节阈值；超过阈值时提示“原图较大，加载可能较慢/占用内存”，并提供「快速预览」；不静默降采样。
- 视频/远端：保持首帧/占位；不生成原图预览。

### 实现记录（2026-11-03）
