## 1. 本轮修了什么（问题 1 + 问题 3）

用户原话：

- **问题 1**：放大预览需要调整，图片挤压会导致周围有空缺。
- **问题 3**：竖图单击聚焦逻辑要修，原本是正常的竖图，单击后却按横图来显示。

### 1.1 根因（四条，均在 `web/src/lib/world.ts`）

| # | 根因 | 表现 |
|---|---|---|
| R1 | `layoutSpotlightCell` 对英雄卡做**单边钳制**：`heroW = Math.max(innerW * 0.46, heroW)` 等四行各自独立夹宽高 | 竖图被硬拉成横框（实测 388×608 的竖图装进 473×397 的框，比例偏差 87%），`object-fit: cover` 裁掉头脚、视觉上"挤压变形" |
| R2 | 邻图只装「一侧整列 + 一带」两个区域，英雄锚在格子**中部**时，上侧 + 非选中侧的 L 形区域完全不装图 | 聚焦图周围成片的 L 形空白（用户截图里的"空缺"） |
| R3 | `gridRects` 网格按 `ceil(n/cols)` 行数排满整个区域，末行不满时**留空槽**（如 3 张图装 2×2 网格，第 4 格空着） | 英雄旁边出现恰好一张卡大小的洞 |
| R4 | 英雄某一侧剩余 3–40px 的**细缝**不收拢 | 视觉上的"细小空缺" |

### 1.2 改动（全部在 `web/src/lib/world.ts`，共三处）

1. **英雄卡只做等比缩放**（`fitHero`）：原图比例装进包围盒（宽支路 60% 宽 × 62% 高，窄支路全宽 × 62% 高），碰到哪条边以哪条边为准；删除全部单边最小/最大钳制。竖图就是竖框、横图就是横框。
2. **邻图区域改为四区域完整剖分**：顶部/底部两条通宽横带 + 英雄左右两段中柱，四块互不重叠、拼起来正好补满格子剩余空间；图少于区域数时丢最小区域（水位分配保证每块 ≥ 1 张且密度均匀）。另加**贴边收缝**：任一侧剩余 < 48px 时英雄向近侧贴齐，把细缝并给另一侧。
3. **`gridRects` 末行 justified**：不满的最后一行按实际张数均分整行宽，区域内部永不留空槽（`layoutFeaturedWorld` 右列同时受益）。

`layoutFeaturedWorld`（有限墙路径）核查过：英雄尺寸本来就是纯等比 fit，末尾钳制为无效代码，未改。

## 5. 用户反例复核（2026-11-10 深夜追加，按指示未修）

### 5.1 反例内容

用户前后对比截图（`30430c00….jpeg`，原图 1414×2000，707:1000 竖图）：

- **点击前**：该图被装在横向卡片里，`object-fit: cover` 重度裁切，只看到中间一带（这本身是墙面的正常行为）。
- **点击后**：聚焦框是竖的、比例正确，**但图片只显示上半截（头顶到手部），卡片下部是一条白色空带**——用户据此判定"还是不对"。

### 5.2 复核过程与实测数据（只读探针，未改任何应用代码）

1. **元数据核对**：`web/public/data/m/0000.json` 中该图 `w:1414 h:2000`，比例 0.707，元数据无误。
2. **稳态几何实测**（`scripts/wall_probe_case.mjs`，经 `#/t/mobius_(honkai_impact)` 过滤墙定位该图并单击）：
   - 聚焦框 435.8×616.4（比例 **0.7070**）；img natural 506×716（**0.7067**）；img 盒子 436.2×617.0（**0.7070**）。
   - `object-fit: cover`、`complete: true`、img 盒子覆盖聚焦框 **100.2%**、卡片背景 `rgb(16,16,18)`（深色，无白色元素）。
   - **结论：布局静态几何完全正确，稳态没有洞。**
3. **瞬态复现**（CDP 网络节流 64KB/s + 300ms 延迟，点击后 500ms/1200ms/2000ms/3500ms/6000ms 连拍，`web/screenshots/repro-midload-*.png`）：
   - **500ms 与 1200ms 截图与用户反例分毫不差**：聚焦框比例正确，图片清晰显示上半截，下部一条白带。
   - 加载完成后白带消失（final：`complete: true`，img 覆盖 100%）。

### 5.3 根因

- 聚焦时 img 的 src 从 t256 换成更高清的 **t1024（该图 234KB）**；`data/t1024/…` 实测是**基线 JPEG（SOF0，非渐进）**，解码自上而下。
- 浏览器对解码到一半的基线 JPEG，**未解码的行渲染为白色**（img 自身表面，不是卡片背景）——于是出现"上半清晰 + 下半白带"。
- 慢环境（首访、冷缓存、慢盘/网络）下整段加载期间白带持续可见；本地快缓存下只是一闪而过，但同样存在。
- **白带不是聚焦布局问题**（§1 的修复方向没有错），而是"聚焦换图直接换 src"的加载瞬态。另外反例截图也再次确认了 §3 问题 2（单击聚焦仍带检查器面板）。

### 5.4 下一轮可选修复方案（按用户指示本轮一律未做）

| 方案 | 效果 | 代价 |
|---|---|---|
| A. 换图前 `img.decode()`：t1024 解码完成后再替换 src，期间保留 t256 的画面（可叠模糊放大） | 白带彻底消失，从"半张白"变成"糊→清晰" | 聚焦大图出现晚约一个加载周期 |
| B. 缩略图重编码为渐进式 JPEG（SOF2） | 整图先糊后清，永无白带 | 需要重跑数据导出管线，存量 937×3 层全重转 |
| C. `.tile__img` 背景从白改为深色 token | 白带变暗带（不再刺眼，但仍是半张空） | 一行 CSS，治标 |
| D. t1024 命中前限制聚焦放大倍率/维持 t256 | 同 A 思路的另一实现 | 同 A |

推荐 A（可顺带 C 兜底）。**以上方案均未实施。**

### 5.6 根因更正（2026-11-11 第二轮取证，推翻 §5.3 对反例图的判定）

- **白带是源图编码内容，不是解码瞬态**：源图 PIL 严格解码成功（非截断 JPEG），第 1640–2000 行是编码进去的纯白 (255,255,255)；t256/t1024 继承同一条白带（≈15.6%/18% 高）。
- 旧 §5.2「加载完成后白带消失」是误判：旧节流连拍 6000ms 截图（`repro-midload-6000.png`）白带仍在；「img 覆盖 100%」只量盒子几何，不量像素。
- 全库扫描（t256 底部连续纯白带 ≥4% 高）：**20/937 张**受影响，含反例图 `db986615`。
- 结论：反例的白带点击前后都在，属源图内容（上传侧垫白/损坏）；§5.4 方案 A（已实施，见 §7.3）只消除健康基线 JPEG 的瞬态白带。**导出层裁剪纯白底带：用户拍板实施，见 §7.9。**

### 7.1 问题 A：墙面竖图被按横图截（`world.ts`）

| 路径 | 根因（实测） | 修法 |
|---|---|---|
| 跨行主图 | 8 探针随机取最接近仍失配 → 0.646 的图装 945×548 横框，仅 37.4% 可见 | 12 探针 + 闸门：\|log(ratio/target)\| ≤ log(1.3) 才做主图，否则退回常规横条 |
| `pickStrip` | 统一拉伸至 1.35×、越过即停补 → 竖图被拉 1.3–1.85× | 记录 \|log(scale)\| 最接近 1 的前缀 + **末位换牌**（64 张窗口里找让整行 scale 更接近 1 的替换）；单卡行换牌仍过最小宽度 |
| `pickColumn` | 顺次取前 N 张 → 单张竖图填宽扁列（0.75 的图装 947×496 列，39.3% 可见） | 按格位比例（slotRatio）选最接近的 wanted 张（64 张窗口） |

实测：离线 245 格 / 2022 张竖图重裁切（<60%）**0**、平均可见 **96.9%**；窄屏 75 格 / 83 张竖图同样 0、平均 97.9%；浏览器 2560×1440 三轮竖图全部 ≥80%（多数 ≈99%）。

### 7.2 问题 B：聚焦后可见尺寸收缩（`world.ts`）

- 根因：60%×62% 包围盒比被点主图大卡小（实测 945×548=518k px² → 聚焦 309k，**0.60×**）。
- 修法：`layoutSpotlightCell`/`layoutFeaturedWorld` 等比 fit 后加**面积保底 = 被点卡面积 × 1.05**，不够等比放大；上限每轴留 ≥88px 给邻图区域（否则横带被压成 <70px 细条——回归抓到的真回归），`SNAP` 48→96 把薄缝并进对侧。
- 实测：浏览器 `--big` 三轮 **1.04× / 3.30× / 3.19×**；离线 1552 种点击情形（100 格逐卡点击）细条 **0**、邻图短边 ≥96；回归 focusSwitch overlap=1。
- 补修（第三轮回归抓到的 flake）：矮横带（88–157px）里图多时 `gridColumns` 旧评分会选两行产出 <70px 细条；加行高/列宽硬下限 70（行数上限反推列数下限）。复扫 1549 情形细条 0。

### 7.3 §5 白带：先解码再换图 + 深色兜底（`WallCard.tsx` / `styles.css`）

- 聚焦时锐利档先离屏 `decode()`，整帧解码完成前保持旧画面（`holdSrc = currentSrc`），完成才换 src；解码失败逐档回退。`.tile__img` 背景 `#101012`（方案 C 兜底）。
- 实测（`wall_probe_case.mjs --throttle`，64KB/s+300ms）：500/1200/2500ms img 保持 t256 且 `complete:true`（无半解码白带），加载完换 t1024，比例偏差 0.14%、覆盖 100.2%。
- **反例图的白带属源图内容，见 §5.6；本修只消除健康文件的瞬态白带。**

## 8. 第三轮：鼠标滚轮 / 触控板（2026-11-11 用户实机反馈）

用户原话：鼠标滚轮向下滚动时偶尔向上回滚且不流畅；触控板只能上下和左右、不支持其他方向；触控板可能失速。

### 8.1 取证（`scripts/wall_probe_wheel.mjs`）

注入鼠标离散 / 触控板连续垂直 / 水平 / 对角 / 捏合序列，逐帧采样 `.world`（inline + computed + MutationObserver + wheel 时间戳）：

- 基线：每场景 **12–36 帧回滚**（反号 >1px）、零速窗 437–528ms、鼠标速度尖峰 p95/p50 ≈ 3.3–5.0。
- 根因：旧版**每个 wheel 事件重启一段 170ms ease-out**；rAF 时间戳可能早于事件时刻（t<0 → k<0），相机向后外推＝回滚；重启另带来速度尖峰。零速窗需按 wheel 时间戳区分「输入暂停后的正确收敛 / 探针投递间隙」与真失速。
- 对角双轴积分原本就生效（x/y 各 -480）；"不支持其他方向"的观感来自回滚与失速。

### 8.2 修法（`Wall.tsx`）

- 单一持久 rAF 循环 + 帧率无关指数平滑：tau 80ms、dt 夹 [0,64]、k=1-exp(-dt/80) ∈ [0,1) 朝累加目标**单调收敛**；离散滚轮与连续触控板共用一条速度曲线，不再每事件重启。
- 捏合锚点改用当前相机（平滑滞后期间光标下世界点不漂），倍率仍累加在目标上。
- `stopGlide` 语义不变：拖拽 / 缩放键 / 回起点立即打断。

### 8.3 复测

| 场景 | 回滚帧（修前→修后） | 活跃期失速 | 速度尖峰 p95/p50 |
|---|---|---|---|
| 鼠标滚轮下 ×12 | 12 → 0 | 0ms | 2.73 |
| 触控板垂直 60 事件 | 28 → 0 | 0–12ms | 1.98 |
| 触控板水平 60 事件 | 27 → 0 | 0ms | 1.89 |
| 触控板对角 60 事件 | 20 → 0（双轴各 -480） | 0ms | 2.07 |
| 触控板长连 120 事件 | 14 → 0 | 0ms | 1.91 |
| 捏合 20 事件 | 0 | 0 | zoom 1→1.6 |

### 8.4 闸门

`wall_shots` 新增 wheel 断言：回滚=0、活跃期失速 ≤80ms、对角双轴位移 ≥100px；探针投递间隙（>60ms 无 wheel）不计失速。gate 自愈：回首页 + 桌面视口 + 关触摸模拟后再注入。

同轮回归闸门校准（几何必然 vs 真缺陷的边界，均经实测取证后改）：

- 细条谓词只查**被重排挤动的卡**：正常格子里 w63×h157 的窄竖卡是墙面内容，旧谓词误伤。
- 换位/teleport 判据改「点击点落在英雄卡内 或 重叠率 ≥0.5」：宽卡+竖英雄的形状差会让重叠率天然 0.3–0.5，但点击点仍被盖住；teleport 两者皆失。
- 「锁中心」加前提：点击点离内容区中心 >150px 且英雄离开点击处 >60px 才算；边缘夹取落到中心附近是几何巧合。
- 概要选卡优先整卡；无整卡样本时回起点换视野再挑，避免半出屏卡溢出误报。
- 键盘用例：程序化聚焦后首键偶发丢失（焦点竞态）补按一次再量；真缺陷会两次都丢。
- 教训：`--out` 传 Git Bash 绝对路径（/d/…）会被 Node 解析成 `D:\d\…` 写到别处，读到的"报告"是旧的——本轮多个"失败"实为此假象；一律用相对路径或 Windows 路径。

## 9. 第四轮：滑动迟滞、不跟手（2026-11-11 用户实机反馈）

用户原话：继续优化滑动效果，现在的感觉有点迟滞，不跟手。

### 9.1 取证：第三轮复测为什么没暴露它

第三轮探针用 CDP 逐事件投递（`Input.dispatchMouseEvent` + sleep），每笔 wheel 一次往返，实测 **wheel 间隔 p50 42–49ms**（名义 16ms）。tau=80 的指数平滑在这么稀的输入下每笔都收敛得差不多，跟随误差只有 13px，看着"还行"；真实触控板是每帧一笔，滞后是**稳态**的。

新增页内等节拍驱动（探针 `cadence()`）：页面里用 rAF 每帧 dispatch 一笔 `WheelEvent`，并在**下一次投递前**读相机，量"新输入到达时上一笔还差多少没跟上"。既避开 CDP 往返抖动，也避开采样器与积分泵在同一帧的先后顺序假象。headless rAF ≈ 6–12ms/帧。

A/B：同一驱动，先把分类临时强制回 tau=80 构建基线，再恢复分类构建（产物 hash 与受测一致）。

| 场景（每帧一笔） | 跟随误差 mean/max：tau=80 → 分类直跟 | 松手收敛尾巴 |
|---|---|---|
| 触控板垂直 dy=12 ×60 | 72.7 / 88.6px → **11.8 / 12px** | 298ms → **11ms** |
| 触控板对角 dx=dy=8 ×60 | 51.6 / 62.8px → **7.9 / 8px** | 272ms → **17ms** |
| 触控板快滑 dy=24 ×90 | 159.9 / 206.3px → **23.7 / 24px** | 356ms → **31ms** |
| 鼠标一格 dy=100 ×12（每 6 帧） | 71.1 / 89.2px → 45.0 / 68.3px | 367ms → 361ms（**有意保留**） |

残留的 12/24px **恒等于一笔增量**，是"事件 → React 提交 → 下一帧可见"的固有下限，不是积分滞后（max 不随速度累积）。

### 9.2 修法（`Wall.tsx`）

新增输入分类 `classifyWheel`，逐事件决定积分时间常数：

- **离散滚轮 → tau=80 glide**：`deltaMode !== 0`（行/页模式，Firefox 与部分鼠标驱动），或像素模式下整数增量且为 100/120 的整格倍（≥40px）。
- **连续流 → tau=0（k=1，逐帧 1:1）**：小数增量（触控板确定信号），或整数小步长（触控板 / 高分辨率滚轮 / OS 惯性）。
- 不做手势状态机：鼠标与触控板混用即时切换；积分泵本身不变（单一持久 rAF、dt 夹 [0,64]、单调收敛累加目标），tau=0 时一帧即 settle，同一帧内多笔事件合并成一次渲染。

### 9.3 直白结论（分开说）

- **跟手：有改善。** 触控板稳态滞后 72.7 → 11.8px（6.2×），快滑 159.9 → 23.7px（6.7×）；残留＝一笔增量的渲染下限。
- **松手收敛：有改善。** 298 → 11ms（27×），不再有"手指停了画面还在走"的尾巴。
- **鼠标滚轮：持平（有意）。** glide 保留，settle 367 → 361ms 属同一档；一格 100px 直跟会像瞬移。
- **回滚：持平（已为 0）。** CDP 六场景 + 等节拍四场景全 0。
- **失速：等节拍连续流 0ms。** CDP 稀投递下出现的 43–49ms 零速窗是**探针投递空窗**（wheel 间隔 p50 42–49ms），直跟下输入停了相机就该停，不是应用失速。

### 9.4 闸门

`wall_shots` wheel 段新增两条等节拍轨迹与断言：

- 触控板：`followMax ≤24px`（两笔增量）、`settle ≤80ms`、回滚 0、失速 ≤80ms。基线 tau=80 的 88.6px / 298ms 会被这两条卡住。
- 鼠标：`settle ≥60ms`——glide 必须还在，防"顺手把离散也改成直跟"的瞬移回归。
- 失速断言从 CDP 触控板轨迹**移到**等节拍轨迹：CDP 突发+空窗下的零速窗是正确行为，旧断言会随机器快慢飘（本轮实测 43ms，逼近 80ms 上限）。

本轮全量回归 `failures: []`；聚焦细条 0、点邻卡 overlap 1 / coversCenter true、捏合 1→1.6、键盘路径（箭头平移 / Tab 进卡 / Enter 开详情）全过。

### 9.5 取证边界（未实机复验）

等节拍驱动用的是**页内合成 `WheelEvent`**，走同一条非被动 native 监听与积分路径，但不是真实触控板硬件。分类判据（小数增量、非整格小步长）对 Windows 精确式触控板与 macOS 触控板的常见增量分布都成立，OS 惯性尾段也按连续流处理；**真实硬件手感仍需用户实机确认**。
